# Versioning

`tbtop/admin` (Packagist) and `@tbtop/inertia-admin` (npm) ship in lockstep
from one git tag, `vX.Y.Z`: the same number always means the same release on
both sides. This page says what a version number promises, what the promise
covers, and how an API is retired.

## What a bump means

### While 0.x (now)

| Bump                | May contain                                                                   |
| ------------------- | ----------------------------------------------------------------------------- |
| Patch — 0.7.**3**   | Fixes, new features and options, deprecations. Nothing that breaks a host.    |
| Minor — 0.**8**.0   | Everything a patch may contain, plus breaking changes.                        |

A breaking change waits for the next minor. Every breaking minor comes with a
section in [UPGRADE.md](UPGRADE.md) that says what to change in the host.

Keep the two packages on the same version: they speak one wire format, and
a mixed pair is not supported. Pin both exactly and bump them in one change:

```json
"tbtop/admin": "0.7.3"
```

```json
"@tbtop/inertia-admin": "0.7.3"
```

A caret range is safe against breaking changes but not against drift:
Composer's `^0.7.3` and npm's `^0.7.3` both stop before 0.8.0, yet a
`composer update` alone can move PHP to a newer patch while npm stays put.

### From 1.0

Plain [SemVer](https://semver.org): a major may break, a minor adds features
and deprecations, a patch only fixes.

## What the promise covers

**Public API**: a breaking change to any of this needs a minor in 0.x (a
major after 1.0).

- PHP: public classes, methods, constants and interfaces under `Tbtop\Admin\`
  that a host calls, extends or implements: the DSL (`S`, fields, columns,
  actions, tables, layout blocks), panel configuration, base pages, facades,
  and the classes `admin:install` publishes into the host.
- The config keys in `config/tbtop-admin.php` and what they do.
- Artisan commands, their arguments and options.
- Route names, translation keys a host can override, and the database schema
  the package's migrations create.
- Everything exported from `@tbtop/inertia-admin` (`.`, `./styles.css`,
  `./styles/*`): `registerBlock`, `defineFieldClient`, the provider and
  registry helpers, and their types.
- The supported PHP, Laravel, Inertia and React ranges. Dropping a version
  is a breaking change; adding one is not.

**Not public API**: these can change in any release.

- Anything marked `@internal`.
- The StructureNode JSON between the two packages (`packages/contracts`). It
  moves in lockstep with both sides; generate it with the DSL and render it
  with the client, never by hand.
- Rendered markup, CSS class names and default styling. The theming and
  appearance APIs are covered; the pixels they produce are not.
- The demo app, the test suites, and the generated API reference's layout.

**Bug fixes.** A fix restores documented behaviour and ships in a patch, even
when a host could have relied on the bug. When a fix is likely to break real
hosts anyway, it waits for the next minor and gets an UPGRADE.md entry.

## Deprecations

An API is deprecated before it is removed, whenever a replacement can exist
side by side with it.

1. **Mark it.** PHP: a `@deprecated` docblock that names the replacement and
   the removal version, plus `trigger_error(..., E_USER_DEPRECATED)` when the
   deprecated path runs. Client: a `/** @deprecated */` JSDoc with the same
   two facts.
2. **Ship it.** A deprecation can land in any release, a patch included, once
   its replacement has shipped.
3. **Remove it.** No earlier than the next minor in 0.x (the next major after
   1.0), and only after the deprecation has been in at least one release. The
   removal version written on a deprecation is a promise: an API marked
   "removed in 1.0" stays until 1.0.
4. **Announce it.** A removal is a breaking change: it gets an UPGRADE.md
   entry and appears under "Breaking changes" in the changelog.

Laravel routes `E_USER_DEPRECATED` to the `deprecations` log channel. Set
`LOG_DEPRECATIONS_CHANNEL` in the host and read that log before upgrading to a
new minor: everything it lists is about to break.

## Supported releases

Only the latest release is supported. There are no backports in 0.x: a fix
ships in the next release of the current line. Security reports:
[SECURITY.md](SECURITY.md).

## Changelog

[CHANGELOG.md](CHANGELOG.md) and the GitHub Release notes are generated by
[git-cliff](https://git-cliff.org) (`cliff.toml`) from the squash-merge
subjects on `main`, so a PR title is its changelog line. Titles follow
`type(scope): subject`:

| Type                                          | Changelog section |
| --------------------------------------------- | ----------------- |
| `feat`                                        | Features          |
| `fix`                                         | Fixes             |
| `perf`                                        | Performance       |
| `revert`                                      | Reverts           |
| `docs`                                        | Documentation     |
| `refactor`, `chore`, `ci`, `build`, `test`, `style` | not listed  |

A breaking change puts `!` before the colon in its PR title,
`feat(php)!: drop Laravel 11`. That `!` is the required marker: it lands the
change under "Breaking changes", whatever its type. A `BREAKING CHANGE: …`
footer adds an explanation, but only counts when it ends up in the squash
commit body; one written only in the PR description never reaches `main`. The release
tooling refuses a patch bump over a breaking commit.
